# 06 · 离线应急流程

> 这份文档是**照着做**的，不是用来读的。建议打印最后一页贴在显示器旁边。

---

## 一、事前：现在就该做的三件事

### 1. 让工具箱在你常用的机器上「能跑」

```bat
ek.cmd selftest
```

期望 11 项全通过。这件事必须**现在**做，不能等出事再做 ——
因为出事时你无法判断「跑不起来」是工具坏了还是环境坏了。

建议在至少两处各放一份：

- 常用工作站（笔记本）
- U 盘或移动硬盘（含整个 `EMERGENCYKITS` 目录，几十 KB，随便放）

> 整个目录**没有第三方依赖**，拷过去就能用。这是刻意的设计：
> 你不需要拷 wheel、不需要拷 conda 环境、不需要保证版本匹配。

### 2. 用演练数据跑一遍，知道「正常输出长什么样」

```bat
ek.cmd demo
ek.cmd triage samples
```

记住几个数字：`samples\` 里有 6 个文件、`sensor.csv` 有 345 行、2 处断档、
1 段卡死、1 个 -999 哨兵值、`app.log` 的 35 条错误聚成 1 类。

**这些数字是校准锚点。** 真出事时如果 `triage` 报告「0 处断档」而你觉得应该有，
你就知道该怀疑工具或怀疑数据，而不是毫无依据地相信屏幕。

### 3. 准备一个「救援目录」的命名习惯

```
D:\rescue\2024-03-01_sensor故障\
    00_原始文件\        ← 只读拷贝，绝不动
    01_triage.md
    02_encoding.md
    03_profile.md
    04_quality.md
    05_anomaly\
    06_ts\
    07_env.md
```

事后再看时，「什么时候跑的、跑的是哪份数据、结论是什么」一目了然。

## 二、事中：五步流程

### 第 0 步：不要在原文件上做任何操作（10 秒）

```bat
mkdir D:\rescue\2024-03-01_事件名
copy 出问题的文件 D:\rescue\2024-03-01_事件名\00_原始文件\
```

哪怕只是 `copy` 一份。磁盘满的时候很容易顺手删东西，删完就再也无法回答
「修之前是什么样」。**现场一旦破坏，所有的复盘都是猜。**

如果磁盘已经满了、连 copy 都不行，先腾出 1 GB（清临时目录），再 copy。

### 第 1 步：一键分诊（1 分钟）

```bat
ek.cmd triage D:\rescue\2024-03-01_事件名\00_原始文件 --out D:\rescue\2024-03-01_事件名\01_triage.md
```

只读这一份报告的**两个地方**：

1. 最上面的「文件类型判定」—— 确认工具认对了类型（如果它把 `.csv` 判成 `text`，
   说明文件内容真的不像表格，这本身就是重要线索）
2. 最下面的「处置建议」—— 按优先级排好的动作清单

中间那一大堆表格先不看。你现在要的是**方向**，不是细节。

### 第 2 步：按症状深入（5–15 分钟）

打开 [03-数据诊断手册](03-数据诊断手册.md) 或 [04-代码诊断手册](04-代码诊断手册.md)
或 [05-系统诊断手册](05-系统诊断手册.md)，找到你的症状对应的那一节。

**每次只查一个假设，并且存档报告。** 因为：

- 存档的报告是复盘时唯一可信的证据
- 「我查了编码，没问题」和「我没查编码」必须能区分开

### 第 3 步：区分「数据错了」和「世界变了」（关键判断）

这是整场急救里最重要的一个判断：

| 证据 | 结论 | 该怎么办 |
| --- | --- | --- |
| `ek env` 有问题（PATH/编码/磁盘/代理） | **环境变了** | 先修环境，之前的分析结论全部作废重跑 |
| `ek code` 报 `CS120`（缺依赖） | **环境变了** | 断网装不上 → 找替代方案或换机器 |
| `ek code` 报 `CS112`（已移除 API） | **库升级了** | 改代码，别怀疑数据 |
| `ek quality` 报 `DQ161`（主键重复） | **数据错了** | 数据问题，环境没问题 |
| `ek` 报告一切正常，但结果就是不对 | **假设错了** | 见下一节 |

这个判断之所以关键：如果你在「环境坏了」的情况下分析数据，得出的所有结论
（包括「数据有问题」这个结论本身）都不可信。

### 第 4 步：当工具说「一切正常」但你确定有问题

这时候问题一定在工具的检查范围之外。按顺序自查：

1. **语义**：单位对吗？列的含义和你以为的一样吗？（`ek profile` 看取值范围是否符合物理直觉）
2. **时间基准**：本地时间 vs UTC？夏令时？跨天拼接？
3. **筛选条件**：你分析的是你以为的那个子集吗？
4. **聚合层级**：行是「每次测量」还是「每天汇总」？
5. **标签泄漏**：建模数据里有没有时间上晚于标签的特征？
6. **上游**：这份 CSV 是怎么生成的？生成它的程序有没有问题？（用 `ek code` 查）

工具箱只保证「结构、编码、分布、时间轴」这四层是干净的。
**语义正确性无法自动化。**

### 第 5 步：记录结论 + 保存证据

```bat
ek.cmd quality 数据.csv --json --out D:\rescue\...\04_quality.json -q
```

JSON 里的 `findings[].code` 是稳定的规则编号，可以在工单/论文脚注/复盘里引用：

> 「事故原因是主键 `sample_id` 重复（`DQ161`），导致两次 merge 后行数从
> 12,400 膨胀到 18,900。」

这比「数据有点问题」有用得多。

## 三、事后：把这次事故变成资产

### 1. 归档

把整个 `D:\rescue\2024-03-01_事件名\` 打包。里面应该有：

```
00_原始文件\        ← 出问题的原始数据（只读副本）
01_triage.md        ← 第一时间的全貌
02…07_*.md          ← 逐步排查的证据
*.json              ← 机器可读的结论（用于统计和检索）
*.png               ← 图（如果出了）
复盘.md             ← 你自己写的：根因、修复方式、如何预防
```

### 2. 复盘三问

1. **如果当时有这个检查，能不能提前发现？**
   能 → 把它加进日常脚本。
2. **这次的结论，下次遇到同类问题能不能直接用？**
   能 → 把具体的规则编号和判读方式补进 `docs/03–05` 对应章节。
3. **工具本身有没有失灵？**
   如果工具报告「正常」但实际有问题 → 这是工具箱的缺口，去
   [07-本次工作说明](07-本次工作说明.md) 的「已知限制」一节看看是不是已列明；
   不是的话，把它变成一个 `selftest` 检查项。

### 3. 积累「判读经验」

工具能给数字，但「R²=0.3 算不算漂移」「覆盖率 92% 算不算正常」需要你的领域知识。
把这些阈值记下来，写进你的项目 README —— 这是任何工具都替代不了的部分。

## 五、三个反模式（别这么做）

### ❌ 一上来就 `dropna()` / `drop_duplicates()` / `fillna(mean)`

你会在统计上「修好」数据，同时把事故现场抹掉。而且：
- `dropna()` 对**整段缺失**完全无效（没有行可删）
- `fillna(mean)` 会把 `-999` 哨兵值也算进均值，然后填一个被污染的均值

先看清楚再决定。

### ❌ 在乱码数据上继续分析

编码错了的时候，字符的对应关系已经丢失。基于乱码做的任何统计、任何模型都是垃圾。
**先解决编码，再谈分析。**

### ❌ 相信「没有报错」

数据事故的绝大多数形态都是**静默的**：`-999` 混在均值里、主键重复让行数翻倍、
时间没排序让滚动窗口错位、编码错了让正则全部失配 —— 它们都不报错。
工具存在的意义，就是把这些不报错的错误变成会出现在屏幕上的结论。
