# 03 · 数据诊断手册

按**症状**查，不按命令查。每条都给「怎么确认 → 怎么判读 → 怎么处理」。

---

## 症状 1：中文变成问号 / 方块 / 一串怪字

这是断网急救里出现频率最高的事故，没有之一。

### 30 秒确认

```bat
ek encoding 数据.csv
```

看三行：

```
推断编码     gb18030
判断依据     候选编码打分最高
把握程度     medium
```

- **把握 `high`** → 基本可以信
- **把握 `medium` / `low`** → 说明 GBK / Big5 / Shift-JIS 之间存在歧义，**必须抽查**

再看「解码替换字符」这一项：大于 0 说明按推断的编码解不干净，数据已经受损。

### 怎么判读

| 现象 | 原因 |
| --- | --- |
| 文件是 GBK，Python 按 UTF-8 读 → 直接 `UnicodeDecodeError` | 最常见；报错反而幸运 |
| 文件是 GBK，被按 `latin-1`/`cp1252` 读 → `ÖÐÎÄ` 这类字符 | 不报错，静默出错，最危险 |
| 文件是 UTF-8，被按 GBK 读 → `涓枃`、`锟斤拷` | 「二次损坏」，原始信息可能已丢失 |
| 带 BOM 的 UTF-8 → 第一列列名变成 `\ufeffid` | `df['id']` 永远 KeyError |

```bat
:: 看文件头，确认是不是你以为的格式
ek encoding 数据.csv --hex
```

zip（xlsx/parquet）应以 `50 4B` 开头；带 BOM 的 UTF-8 以 `EF BB BF` 开头；
UTF-16 会有大量 `00`。

### 怎么处理

**先备份，再转码**（工具不会覆盖你的原文件）：

```bat
ek encoding 数据.csv --convert utf-8 --to 数据_utf8.csv
ek quality 数据_utf8.csv          :: 转完立刻验证中文没被破坏
```

如果文件其实是 UTF-8 但你怀疑被别的程序错误转码过，**不要**在乱码上继续分析 ——
乱码里的字符对应关系已经丢失，任何统计结论都无意义。找回原始文件才是正解。

在代码里读的时候，永远显式写编码：

```python
pd.read_csv("data.csv", encoding="utf-8-sig")   # 有 BOM 也能正确读
pd.read_csv("data.csv", encoding="gb18030")     # GBK 的超集，比 "gbk" 更宽松
```

> 工具箱自己的每条命令都传 `encoding=`，`ek code` 会把漏写编码的 `open()` 标成
> `CS104` —— 这是同一个坑的另一面。

## 症状 2：列名对不上 / `KeyError: 'value'`

### 30 秒确认

```bat
ek profile 数据.csv --head 3
```

列画像表格会原样列出所有列名（含首尾空格，用引号能看出来）。常见的四种列名事故：

| 现象 | 规则编号 | 处理 |
| --- | --- | --- |
| 首列是 `\ufeffid` | `DQ010` | 用 `encoding="utf-8-sig"` |
| 列名重复（`浓度` 和 `浓度`） | `DQ104` | 重命名；重复列名会让 `df['x']` 返回 DataFrame 而不是 Series |
| 列名带首尾空格 / 双空格 | `DQ105` | `.columns = [c.strip() for c in df.columns]` |
| 第一行数据被当成表头 | 见下 | 检查文件是否真的没有表头 |

### 「第一行数据被当成表头」

`profile` 里会看到列名本身是一个数值，而且行数比预期少 1：

```
规模: 199 行 × 1 列
| 列名     | 类型 | 非空 | 唯一值 |
| 101.4357 | 浮点 |  199 |    199 |
```

单列纯文本（每行一个值）会自动识别这种情况并回退成 `value` 列名。多列文件请显式确认：

```bat
ek profile 数据.csv --head 5      :: 看前 5 行原始内容，判断到底有没有表头
```

## 症状 3：行数变多了

**这几乎总是 merge 造成的，而 merge 出问题的根源几乎总是主键不唯一。**

### 30 秒确认

```bat
ek quality 数据.csv --key id
```

```
[XX] DQ161  主键不唯一：id
         → 细节=3 个键值重复，最频繁的：[('S004', 2), ('S007', 2)]
         → 建议=主键重复会让 merge 产生笛卡尔积，行数凭空翻倍 —— 这是最常见的「数据变多了」事故
```

### 其他可能

| 规则编号 | 含义 |
| --- | --- |
| `DQ150` | 完全重复的行（重复采集 / 合并时重复 append） |
| `DQ102` | 字段数与表头不一致（字段里有未转义的分隔符，导致某一行被拆成两行） |
| `DQ130` | 时间戳重复（时序数据「重采样后变多」的元凶） |

### 处理

```python
# 确认重复是真的重复，还是多次实验的合法重复
bad = df[df.duplicated("id", keep=False)]
print(bad.sort_values("id").head(20))
```

不要无脑 `drop_duplicates()` —— 如果 `S004` 的两条记录内容不同，那是数据冲突，
需要人工裁决，而不是删掉一条。

## 症状 4：行数变少了 / 某段时间的数据没了

### 30 秒确认

时序数据用 `ts`，它会给出**断档的具体位置和估计缺失点数**：

```bat
ek ts 数据.csv --time timestamp --value value
```

```
== 三、缺失与断档 ==
[!!] TS111  发现 2 处时间断档，估计缺失 16 个采样点
         → 建议=断档期间到底是「没采集」还是「采集了没存」，两种情况的处理完全不同
+---------------------+---------------------+-----------+--------------+
|      上一个点       |      下一个点       |   间隔    | 估计缺失点数 |
+---------------------+---------------------+-----------+--------------+
| 2024-03-01 01:59:00 | 2024-03-01 02:15:00 | 16m 00.0s |           15 |
| 2024-03-01 05:29:00 | 2024-03-01 05:31:00 | 2m 00.0s  |            1 |
+---------------------+---------------------+-----------+--------------+
```

同时看「覆盖率」：实际点数 / 理论点数。上面这个例子是 95.8%。

### 怎么判读

| 特征 | 含义 |
| --- | --- |
| 断档之间间隔很规则 | 采集程序定时重启 / 定时任务有间隙 |
| 断档正好跨整点 / 整分 | 分文件存储的边界没拼接上 |
| 断档期间**完全没行** | 「没采集」；下游 `dropna()` 看不出来，是最阴险的一种 |
| 断档期间**有行但值为空** | 「采集了没存」；至少知道该时刻有心跳 |
| 覆盖率 100% 但时间戳重复 | 重复采集，实际有效点可能更少 |

### 处理

- **不要**默认用插值填满：断档 16 分钟可能是仪器真的停了，插值会凭空造出数据。
- 在论文/报告里必须说明缺失机制（MCAR / MAR / MNAR）。
- 如果确实要插值，先存一份「原始 + 缺失标记」的数据，保证可回溯。

## 症状 5：缺失值到处都是

### 30 秒确认

```bat
ek quality 数据.csv
```

```
[!!] DQ113  缺失率偏高：value
         → 细节=1/343 行缺失（0.3%）
[--] DQ114  疑似缺失标记：浓度(ppm)
         → 细节=1 个值形如 - ? unknown 等
```

`DQ114` 是**疑似**缺失：`-`、`?`、`unknown`、`未知` 这些值既可能是缺测标记，
也可能真是合法取值。工具不敢替你判断，所以单独一档报出来。

### 怎么判读缺失机制

```bat
ek profile 数据.csv --hist      :: 看分布形状
```

| 观察 | 可能是 |
| --- | --- |
| 缺失均匀散布 | MCAR（完全随机缺失） |
| 缺失集中在某段时间 | 传感器/网络故障 |
| 缺失集中在某类样本 | MAR（与观测到的变量相关） |
| 缺失与「值很大」相关（比如只在高温时缺） | MNAR（与缺失值本身相关）—— 最麻烦 |

后两种不能简单插值，需要用模型（多重插补等）或在分析里显式处理。

### 哨兵值：能骗过缺失值检查的那一类

传感器常用 `-999` / `9999` 表示缺测，而不是留空。这类值**不是缺失**，
它们会老老实实参与 `mean()`：

```bat
ek anomaly 数据.csv --column value
```

```
| 数据行号 |        时间         |  原始值  |     命中方法      | 票数 |
|      246 | 2024-03-01 04:20:00 | -999.000 | iqr，jump，modz，z |    4 |
```

四票命中的 `-999` 几乎不可能是真实测量值。处理：

```python
df.loc[df["value"] == -999, "value"] = np.nan    # 先转成真缺失，再谈填充
```

工具会把它标成 `DQ117`，但**不会**自动改 —— 也许你的实验里 -999 真是合法值。

## 症状 6：数值看着不对（尖峰 / 漂移 / 卡住）

### 30 秒确认

```bat
ek anomaly 数据.csv --column value
```

```
各方法命中：z=1  modz=3  iqr=6  jump=6
-- 按可疑程度排序（前 9 个）
| 数据行号 |  原始值  |      命中方法      | 票数 | 最高得分 |
|      246 | -999.000 | iqr，jump，modz，z |    4 |    165.9 |
|       41 |  141.459 | iqr，jump，modz    |    3 |    13.71 |
|      247 |   53.880 | jump               |    1 |    136.6 |
```

**判读方法：看票数和「说明」列。**

- 票数 4 = 四种方法的假设都被触发 → 几乎肯定是问题
- 票数 3 = 大概率是问题
- 票数 1 且命中的是 `jump` → 它是尖峰**之后**的那个点（因为「变化大」），
  不是尖峰本身。这是 `jump` 的固有特性，看「说明」里的相邻变化量就能判断
- 只被 `z` 命中 → 数据重尾，多半是误报

### 三种典型故障的区别

| 现象 | 特征 | 用哪个命令 |
| --- | --- | --- |
| **孤立尖峰** | 单点异常，前后正常 | `anomaly`（`jump` + `modz` 都能抓） |
| **缓慢漂移** | 整体在移动，没有单点异常 | `ts`（看「线性趋势」和 R²） |
| **卡死** | 一段时间内数值完全不变 | `ts`（看「疑似传感器卡死」的平直段） |

漂移和卡死在 `anomaly` 里**可能完全看不出来** —— 漂移期所有点都正常，
卡死期所有点都等于前一个值。这是必须用 `ts` 的原因。

```bat
ek ts 数据.csv --time timestamp --value value
```

```
| 线性趋势 | -0.3692 / 小时 |
| 趋势 R²  | 0.0671         |

[!!] TS120  存在 1 段连续相同取值
         → 建议=连续不变通常是串口断线/程序卡住后保持最后值，不是「数据很稳」
| 长度(点) | 开始行号 | 结束行号 | 持续时长  | 取值 |
|       20 |      266 |      285 | 19m 00.0s | 62.5 |
```

R² 很低但斜率不为 0，通常只是噪声；R² > 0.5 且斜率显著，才是真漂移。

## 症状 7：时间轴本身有问题

`ts` 会一次性检查七项：

| 检查 | 规则 | 危险信号 |
| --- | --- | --- |
| 采样间隔 | `TS104` | 规整度 < 95%；或有明显的第二个间隔（变频采样/跨天拼接） |
| 断档 | `TS111` | 见症状 4 |
| 重复时间戳 | `TS101` | 重采样时同一时刻被重复加权 |
| 时间倒序 | `TS102` | 画图会出现来回折线 |
| 覆盖率 | — | < 90% 说明大面积缺失 |
| 平直段 | `TS120` | 见症状 6 |
| 周期 | `TS140` | 自相关峰，可用于确认采样耦合/日周期 |

**时间倒序特别值得一说**：数据没排序时，`rolling()` 会按行顺序滚，
于是「第 5 分钟」可能排在「第 7 分钟」后面，滚动均值完全失真，而且不报错。

```python
df = df.sort_values("timestamp").reset_index(drop=True)   # 分析前第一件事
df = df.drop_duplicates("timestamp", keep="last")         # 再去重
```

## 症状 8：数据检查全绿，但结论还是不对

工具能查的是**结构**和**分布**，查不了**语义**。这时候按下面顺序自查：

1. **单位**。`value` 是 ℃ 还是 K？是 Pa 还是 hPa？量级差 100 倍时，任何异常检测
   都会把整列判为异常或整列判为正常。看 P02/P98 的量级是否符合物理直觉。
2. **时间基准**。是本地时间还是 UTC？有没有夏令时？有没有丢闰秒？
   时间列里出现整数天偏移（`TS` 里断档恰好 24h）通常是时区问题。
3. **筛选条件**。你分析的是全量还是子集？子集是怎么定义的？有没有把对照组的条件
   写进筛选里？
4. **聚合层级**。行是「每次测量」还是「每天汇总」？混淆二者的统计量没有意义。
5. **标签泄漏**。如果这是建模数据，检查是否有某个特征在时间上晚于标签。

`profile` 的价值就在这里：它把「每一列长什么样」摊开，让语义错误无处可藏。

## 症状 9：完全不知道从哪下手

一条命令：

```bat
ek triage 数据.csv --out 分诊报告.md
```

或者给整个目录：

```bat
ek triage D:\labdata
```

它会：判断类型 → 跑数据质量 → 列画像 → 数值列异常扫描 → 时间轴 →
（如果是日志/代码则跑对应检查）→ 最后给「处置建议」，把命中的规则编号翻译成
按优先级排好的动作清单。

**然后从这个报告出发，用上面 1–8 的某一节深入。**

## 一份完整的 15 分钟流程（真实场景模板）

```bat
:: 0. 先存档原始文件（只读，不动）
mkdir D:\rescue_20240301
copy D:\labdata\sensor.csv D:\rescue_20240301\

:: 1. 分诊
ek triage D:\labdata\sensor.csv --out D:\rescue_20240301\01_triage.md

:: 2. 编码（分诊里提示 DQ010/DQ014 时）
ek encoding D:\labdata\sensor.csv --out D:\rescue_20240301\02_encoding.md

:: 3. 结构
ek profile D:\labdata\sensor.csv --hist --head 10 --out D:\rescue_20240301\03_profile.md

:: 4. 质量
ek quality D:\labdata\sensor.csv --key timestamp --out D:\rescue_20240301\04_quality.md

:: 5. 异常
ek anomaly D:\labdata\sensor.csv --column value --plot D:\rescue_20240301\05_anom.png
ek anomaly D:\labdata\sensor.csv --column value --out D:\rescue_20240301\05_anom.md

:: 6. 时序
ek ts D:\labdata\sensor.csv --time timestamp --value value --plot D:\rescue_20240301\06_ts.png
ek ts D:\labdata\sensor.csv --time timestamp --value value --out D:\rescue_20240301\06_ts.md

:: 7. 环境（怀疑跟机器有关时才跑）
ek env --out D:\rescue_20240301\07_env.md
```

**全部只读。** 原文件一个字节都没动。报告、图、JSON 全部落在 `rescue_20240301\`，
可以整体打包发给别人或留档复盘。
