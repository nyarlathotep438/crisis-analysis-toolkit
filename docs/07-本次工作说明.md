### 从这些内容里提炼出的四个缺口

1. **只有"看"，没有"判断"**。`quick_overview` 打印缺失数，但不告诉你 12% 缺失算不算问题、
   是随机的还是成块的。所以工具箱的每条输出都必须带**结论 + 证据 + 建议**，而不只是数据。
2. **单一方法不可靠**。z-score 在重尾分布上误报、在掩蔽效应下漏报。所以异常检测要做成
   **多方法投票**，并把每种方法的失效条件写进文档。
3. **时间轴没有被当作检查对象**。断档、重复时间戳、传感器卡死、缓慢漂移 —— 这些
   画图看不出来（画出来是一条平线，看起来"很稳"），必须专门检查。
4. **缺"环境/代码"这一半**。你的 notebook 里有一处 `pd.date_range(..., freq="T")` 触发
   `FutureWarning`（`T` 将被移除）—— 这正好说明"代码/环境问题"和"数据问题"是同一场事故的
   两个半场，工具箱必须都能覆盖。

## 四、从 notebook 到脚本：具体怎么扩的

这是本次工作的核心：**不是把 cell 抄成脚本，而是补上"从数据到结论"的那一层。**

### 4.1 `StructureQuickCheck` → `ek profile`

| 原有 | 扩展为 |
| --- | --- |
| `print(df.shape)` | 行 × 列 + 文件大小 + 编码 + 分隔符 + 是否被截断 |
| `print(df.columns.tolist())` | 逐列画像表（类型/非空/缺失率/唯一值/范围/中位） |
| `display(df.head())` | 前 N 行原样展示（`--head`，可关） |

### 4.2 `SimpleAbnormalCheck` → `ek anomaly`

| 原有 | 扩展为 |
| --- | --- |
| `zscore_anomaly(df, col, 3)` | `z` 方法（保留，但标注"会被异常点自身污染"） |
| `df[col].rolling(10).mean()/std()` | `roll` 滚动 z-score（因果窗口，可用于在线判断） |
| — | `modz` 修正 z-score（中位数 + MAD，抗掩蔽） |
| — | `iqr` 四分位距（不假设分布）；**IQR 退化为 0 时有条件降级** |
| — | `jump` 跳变检测（专抓"某一刻突然错了"） |
| — | `cusum` 累积和（专抓缓慢漂移的起点） |
| — | **投票共识**：按票数排序，票数 ≥2 才值得优先核对 |

关键改动：原实现只有一个阈值，而真实数据里"一个 0.1% 的灾难性错误"会被
z-score 自己算出的标准差掩盖掉。多方法投票解决的就是这个问题。

## 五、关键设计决策

### 5.1 零第三方依赖（最重要的一条）

**决策**：主路径只用标准库；numpy/pandas/matplotlib 只作为"可选增强"。

**理由**：诊断工具的失效时刻，恰恰是环境最可能已经坏掉的时刻。
一个"需要 pandas 才能诊断"的工具在这个场景下是自相矛盾的。

**代价**：纯 Python 数值计算慢。实测 345 行 × 3 列整表画像 30 ms，
20 万行以内无感；超过请用 `--max-rows`。

**被否决的方案**：直接用 pandas 写（代码能短一半）。否决原因是它把
"工具能不能跑"和"环境好不好"绑成了同一件事。

### 5.2 只读默认

**决策**：任何命令都不改动输入文件。写文件必须显式 `--out` / `--to` / `--plot`。

**理由**：急救最怕破坏现场。删掉一份重复文件之后，你就再也无法回答
"修之前是不是这样"。

**具体体现**：连"转码"这种天然要写文件的功能，也要求 `--to` 指定新文件，
或 `--inplace` 且自动备份 `.bak`。

### 5.3 结论必须带证据和建议

**决策**：每条结论 = 编号 + 一句话 + 证据 + 建议动作。

```
[!!] DQ161  主键不唯一：sample_id
         → 细节=3 个键值重复，最频繁的：[('S004', 2), ('S007', 2)]
         → 建议=主键重复会让 merge 产生笛卡尔积，行数凭空翻倍 —— 这是最常见的「数据变多了」事故
```

**理由**：只报"有 3 个重复值"不构成可用信息，你还得自己想"这意味着什么"。
在凌晨三点的急救现场，这个"想"的成本极高。

### 5.4 规则编号

**决策**：每条结论有稳定编号（`DQ161`、`ENV007`、`CS104`…）。

**理由**：让结论可被引用。"上次是 `DQ161`"比"上次数据有点问题"有用一个数量级。
编号也方便 `--json` 导出后做统计：哪些规则最常被触发，就是最该预防的问题。

### 5.5 中文终端适配（三个具体问题）

| 问题 | 处理 | 如果不处理会怎样 |
| --- | --- | --- |
| 中文字符占 2 列但 `len()` 返回 1 | `display_width()` 用 `east_asian_width` | 表格整体错位 |
| 画框字符 `│┼` 在 cp936 下无法编码 | 边框只用 `+ - \|` | 重定向到文件时 `UnicodeEncodeError` 崩在最后一步 |
| sparkline 方块字符在窄字符集下不可用 | 运行时探测，降级到 `. :-=+*#%@` | 同上 |

另外 stdout 统一 `reconfigure(errors="replace")`：万一是别的编码，
字符变 `?` 而不是崩。

### 5.6 异常检测多方法投票

**决策**：不用单一方法，六种方法各算一遍，按票数排序。

**理由**（这是本次最实质的算法决策）：单一 z-score 有两个致命失效：

- **掩蔽效应**：异常点把均值和标准差一起拉大，z 分数反而不到阈值 3。
  29 个 `10.0` 加 1 个 `100.0`，z-score 认为 `100` 不算异常。
- **漂移误报**：整体抬升 20% 时，漂移期间所有点都被判异常，你在几百个"异常"里
  找不到真正的那个跳变。

投票让不同假设的错误互相抵消：只被一种方法命中的点标"票数 1"（多半是该方法的偏好），
被 3–4 种方法同时命中的点才是真问题。

### 5.7 缺失值分两档

**决策**：`NA/NaN/空串` 是确定缺失；`-`/`?`/`unknown` 是疑似缺失，分开统计。

**理由**：`-999` 这类哨兵值混进 `mean()` 时**不会报错**，是最难查的静默污染。
但工具也不敢直接把它当缺失 —— 也许你的实验里 `-999` 真是合法值。所以分开报，
由人决定。

### 5.8 类型推断用 95% 而非 100%

**决策**：≥95% 的值能解析成数字，就算数值列，剩下 5% 单独报 `DQ115` 并排除出统计。

**理由**：要求 100% 的话，一个错字就让整列退化成"文本"，于是所有数值检查
**静默跳过** —— 这比报错危险得多。

### 5.9 用法错误返回 3 而不是 2

**决策**：覆盖 `argparse` 的默认行为，参数错误退出码用 3。

**理由**：0/1/2 是"发现问题的严重程度"，如果参数写错也返回 2，脚本里
`if errorlevel 2` 就无法区分"数据坏了"和"我把 `--column` 打错了"。

## 七、已知限制

诚实列出来，比事后被发现好。

### 7.1 能力限制

| 限制 | 影响 | 缓解 |
| --- | --- | --- |
| 纯 Python 数值计算 | 百万行级数据慢 | `--max-rows`；或临时装 numpy/pandas |
| 编码探测是启发式的 | GBK/Big5/Shift-JIS 有客观歧义 | 显式给出"把握程度"，`medium`/`low` 时要求人工抽查 |
| 已移除 API 用文本匹配 | 字符串里含同样文字会误报 | 标 `warn`、说明"可能误报"、提供 `# noqa` |
| 重复文件大文件用"首尾 64KB+大小"指纹 | 理论上有碰撞可能 | 报告写明判定方式；只报"疑似"，不自动删 |
| 异常检测是启发式的 | 无法保证"真正异常" | 多方法投票 + 文档写明每种方法的失效条件 |
| 时间格式只认常见写法 | 自定义格式会被漏判 | `--time` 可显式指定；无法解析时会明确报 `TS103` |
| 不解析 Excel 公式 / 合并单元格 | xlsx 只能靠 pandas 读成平面表 | 建议先另存为 CSV |

### 7.2 覆盖不到的问题类型

- **语义错误**：单位搞错、列含义理解错、时间基准错 —— 工具只能提示"取值范围是否符合直觉"
- **统计设计错误**：样本量不足、多重比较、混杂因素
- **逻辑错误**：代码能跑、数据干净，但算法本身错了
- **并发/性能问题**：需要 `py-spy` / `perf` / `cProfile`
- **网络与硬件故障**：需要系统自带工具

### 7.3 平台验证范围

- **开发和验证环境**：Windows 11 + Python 3.13.5（Anaconda）
- **`ek.sh`**：已写好但**未在 Linux/macOS 实机验证**（本次会话只有 Windows 环境）。
  代码只用了 `os` / `sys` / `shutil` 的跨平台子集，理论上可用；如遇问题请改用
  `python3 -m ekits`。
- **Python 版本**：代码用了 `from __future__ import annotations`、`sys.stdlib_module_names`（3.10+）、
  `str.removeprefix` 之类的 3.9+ 特性。**声明支持 3.9+，实际只在 3.13 验证过。**

## 八、如何扩展（加一条新命令只需三步）

以"加一个检查重复列名相似度"的命令为例：

### 第 1 步：写计算模块（不打印）

```python
# ekits/similarity.py
from dataclasses import dataclass

@dataclass
class Suggestion:
    left: str
    right: str
    score: float

def near_duplicate_columns(columns, threshold=0.85):
    """返回列名高度相似的对。纯计算，不打印、不写文件。"""
    out = []
    for i, left in enumerate(columns):
        for right in columns[i + 1:]:
            score = _ratio(left, right)
            if score >= threshold:
                out.append(Suggestion(left, right, score))
    return sorted(out, key=lambda s: -s.score)
```

### 第 2 步：在 `cli.py` 里装配命令

```python
def cmd_similarity(args) -> int:
    rep = report.Report("列名相似度", target=args.path)
    table = _load(args, args.path)
    hits = similarity.near_duplicate_columns(table.columns, args.threshold)
    rep.section("一、结论")
    if hits:
        rep.warn("SIM001", f"有 {len(hits)} 对列名高度相似", 建议="确认是不是重复录入")
        rep.table(["左", "右", "相似度"],
                  [[h.left, h.right, fmt.num(h.score)] for h in hits])
    else:
        rep.ok("SIM002", "没有高度相似的列名")
    return _emit(rep, args)          # ← 统一出口：终端 + --out / --json
```

### 第 3 步：注册参数

```python
    sub_s = sub.add_parser("similarity", help="列名相似度检查")
    sub_s.add_argument("path", metavar="文件")
    sub_s.add_argument("--threshold", type=float, default=0.85)
    _add_common(sub_s)               # ← 自动获得 --json / --out / -q
    sub_s.set_defaults(func=cmd_similarity)
```

1. 计算模块不 `print`，返回 dataclass
