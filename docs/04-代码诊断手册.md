# 04 · 代码诊断手册

> 前提：这里**不执行**你的代码，只做静态分析。所以它不联网、不会污染环境、
> 也不会因为你的代码有副作用而卡住。

---

## 症状 1：`ModuleNotFoundError` / `ImportError`

### 30 秒确认

```bat
ek code <项目目录>
```

第三部分「依赖可用性」会逐个检查顶层导入：

```
[!!] CS121  有 1 个导入在当前环境里不可用
         → 建议=断网无法安装：确认是否装在别的 conda 环境，或换成标准库实现
[XX] CS120  导入的模块不可用：pyarrow（出现在 pipeline.py:12）
```

### 怎么判读

| 情况 | 判断依据 | 处理 |
| --- | --- | --- |
| 拼写错误 | 模块名不像常见包（`reqeusts`） | 改名 |
| 装错环境 | `ek env` 显示 PATH 里多个 python | 用正确的解释器，或 `python -m pip install` 明确装到当前解释器 |
| 本地文件遮蔽 | 项目里有同名 `.py`（如 `json.py`） | 改名；`ek env` 会报 `ENV012` |
| 真的没装 | 包名正常但 `find_spec` 返回 None | 断网时装不上 → 找替代实现或用另一台机器 |

### 断网时的替代路线

这一条比修代码更重要：**先确认哪些依赖是「关键路径」**。

```bat
ek code <目录> --json --out deps.json -q
```

导出后按 `CS120` 过滤，得到「缺了就跑不起来」的清单。然后分三类：

1. **能删**：只在报错分支/废弃函数里用的 → 删掉或改成延迟导入
2. **能替**：`pyarrow` → 换 CSV；`matplotlib` → 用 `ts` 的文本 sparkline
3. **不能替**：核心算法依赖 → 只能等网络恢复，但至少你现在**知道**卡在哪

## 症状 2：昨天能跑，今天跑不起来

环境变了、或者文件之间出现了隐蔽依赖。两条命令：

```bat
ek env          :: 环境层面：解释器、PATH、编码、磁盘、代理、PYTHONHOME
ek code <目录>   :: 代码层面：语法、反模式、已移除的 API、notebook 执行顺序
```

`ek env` 里值得逐条看的：

| 编号 | 检查 | 典型症状 |
| --- | --- | --- |
| `ENV001` | `PYTHONHOME` 被设置 | import 随机失败、pip 装到奇怪的地方 |
| `ENV007` | PATH 里有多个 python | `pip install` 成功但 `import` 找不到 |
| `ENV012` | 本地文件覆盖标准库 | `AttributeError: module 'json' has no attribute 'loads'` |
| `ENV013` | `sys.path` 含当前目录 | 「在 A 目录能跑，在 B 目录不能」 |
| `ENV015` | 运行在 `-O` 模式 | 你机器上被 `assert` 拦住的错误，在别人机器上静默通过 |
| `ENV006` | stdout 编码不是 UTF-8 | 本地没事，重定向到文件就 `UnicodeEncodeError` |

还有一类最常见的「昨天能跑」：**库版本升级后 API 被移除**。`ek code` 会文本匹配
这些模式（规则 `CS112`）：

| 已移除 | 替代 |
| --- | --- |
| `df.ix[...]` | `.loc` / `.iloc` |
| `df.append(...)` | `pd.concat([...])` |
| `df.applymap(...)` | `.map(...)` |
| `np.float` / `np.int` / `np.bool` | 内置 `float` / `int` / `bool` |
| `np.NaN` / `np.Inf` | `np.nan` / `np.inf` |
| `pd.datetime` | `pd.Timestamp` |
| `.iteritems()` | `.items()` |

> 这是**文本匹配**，字符串里出现同样的字也会命中，所以标成 `warn` 而不是 `error`。
> 确认无误的行可以在行尾加 `# noqa` 豁免。

## 症状 3：程序没报错，但结果不可信

这是最难查的一类，因为没有任何信号。工具箱重点抓「静默出错」的四种模式：

| 规则 | 模式 | 为什么危险 |
| --- | --- | --- |
| `CS101` | `except:` 裸捕获 | 连 `KeyboardInterrupt`、`SystemExit` 都吞掉，Ctrl+C 停不下来 |
| `CS102` | `except Exception: pass` | 错误被彻底忽略，**之后所有结果都不可信** |
| `CS103` | 可变默认参数 `def f(cache={})` | 默认值只创建一次，多次调用共享同一个 dict —— 跨样本污染 |
| `CS104` | `open()` 不写 `encoding=` | Windows 用 GBK、Linux 用 UTF-8，同一份代码两台机器读出不同内容 |

其中 `CS104` 最值得展开，因为它同时造成两种故障：

```python
# 事故 A：在 Windows 上读 GBK 文件正常，在 Linux 上 UnicodeDecodeError
text = open("data.txt").read()

# 事故 B：读 UTF-8 文件，Windows 上静默读出乱码，后续正则全部失配
```

修法只有一条：**永远写 `encoding=`**。二进制模式（`"rb"`）不需要，工具也会跳过。

### `CS103` 的真实危害

```python
def load(path, cache={}):        # ← 这个 {} 只创建一次
    if path not in cache:
        cache[path] = read(path)
    return cache[path]

load("a.csv")   # cache = {"a.csv": ...}
load("b.csv")   # cache = {"a.csv": ..., "b.csv": ...}
```

单次运行看起来完全正常。但如果循环里处理 100 个文件、或者用 `multiprocessing`
派生进程，就会出现莫名其妙的「结果串了」。而且这个 bug 只在**第二次调用**时暴露。

## 症状 4：notebook 跑不通 / 结果和上次不一样

```bat
ek code 分析.ipynb
```

notebook 的四个专属检查：

| 规则 | 检查 | 为什么重要 |
| --- | --- | --- |
| `NB002` | 保存着**报错输出** | 说明这份 notebook 上次没跑通就被存了，你看的结论可能来自更早的运行 |
| `NB003` | **执行顺序**不是从上到下 | 「重启后跑不通」的头号原因：变量来自更早的单元格 |
| `NB004` | 有代码单元格**从未执行** | 未执行的代码不代表可用 |
| `NB005` | 源码里有**绝对路径** | 换个目录就跑不了 |
| `NB006` | kernel 的 Python 版本与当前解释器不一致 | 跨小版本可能有行为差异 |

### 最该处理的是 `NB003`

```
[!!] NB003  单元格执行顺序不是从上到下
         → 执行计数序列为 [3, 4, 5, 6, 1, 2, 7]
```

这说明你现在的变量状态**不能**由从上到下执行复现。在论文里这是可复现性问题，
在工程里这是「本地能跑，CI 跑不了」。

**验证方法**：Kernel → Restart & Run All。如果跑通了，说明只是顺序问题（改代码走
回头重跑过）；如果跑不通，说明你依赖了某个已经被删除的中间状态 —— 那就真的需要修了。

### 顺带一个习惯

把 notebook 里的函数搬到 `.py` 文件里（哪怕只是 `src/utils.py`），
然后 notebook 只留 import 和调用。这样 `ek code` 能对逻辑做 AST 级检查，
而不是只能看 notebook 的元数据。

## 误报豁免

静态检查必然有误报。工具箱提供两级豁免：

**行级** — 在该行末尾加 `# noqa` 或 `# ek:ignore`，这一行的所有检查都跳过：

```python
except Exception:  # noqa: CS102 - 可选依赖探测失败就退回标准库方案，属于预期
    pass
```

**文件级** — 在文件前 40 行内写 `# ek:ignore-file CS112,CS108`：

```python
"""某个把"已移除 API"写成字符串的迁移脚本。"""

# ek:ignore-file CS112      # 本文件要匹配这些模式，会自己举报自己
```

> 工具箱自己的 `codescan.py` 和 `demo.py` 就用了文件级豁免，`selftest.py` 用了
> `CS108` 豁免（自检的判断依据就是 assert）。加上豁免之后，`ek code ekits` 的结果是
> **0 命中** —— 这是「工具能对自己用」的最低标准。

## 和其他工具的边界

| 工具 | 它更擅长 | 什么时候还该用 |
| --- | --- | --- |
| `ek code` | 断网时快速扫一遍「能不能跑 / 会不会静默出错 / 缺什么依赖」 | 应急第一遍 |
| `pylint` / `ruff` | 代码风格、复杂度、未使用变量 | 日常开发 |
| `mypy` | 类型正确性 | 有类型标注的项目 |
| `pytest` | 行为正确性 | 有测试的项目 |
| `py-spy` / `cProfile` | 性能热点 | 卡顿问题 |

`ek code` 的定位不是替代它们，而是**在它们都装不上/跑不起来的时候，还能给你一份
有优先级的清单**。
